# WEB007-EASE — independent API administration design Critic

Verdict: **PASS for the proposed design, conditional on the focused implementation checks below.** This is design acceptance, not a claim that the vault is implemented, tested or released. No old tests, new provider calls or mutations were performed. Reviewed: EASE_OF_CREATION.md and the existing AuthService, HTTP/CSRF, AtomicRepository, ProviderRegistry, provisioner and host Compose contracts.

The specification correctly separates global system administration from tenant ownership, credential storage from adapter availability, and budget preferences from paid-execution approval. AES-256-GCM with a persistent private server key is suitable for keeping credentials out of ordinary state inspection, provided initialization, nonce uniqueness, integrity and authorization remain fail-closed.

## Required authority boundaries

`manage_integrations` must derive only from the current configured identity's literal `system_admin === true`, or the genuine host-operator fallback when no identity file is configured. Never grant it by the string id `host-operator` alone: a configured file can contain that id without system_admin. A configured identity file remains authoritative; a missing/invalid file must not silently reactivate fallback administration. Tenant owner/admin, can_create_tenants, membership records and request-body fields must never confer this global permission.

Resolve the session and current identity for every vault read, save, delete and budget update in the service layer. HTTP/UI gating alone is insufficient. Invalidate access immediately on identity disablement, credential rotation or system_admin removal. Recheck current permission when a mutation has waited behind another transaction, so a queued operation does not commit using an earlier cached role. Preserve existing sessions and memberships; this feature does not authorize automatic role promotion or creation of reviewer identities.

The current provisioner does not expose system_admin. Document the deliberate administrator provisioning mechanism or add an explicit local-only provisioner flag; do not make --can-create-tenants a substitute. Keep the identity file private and authoritative.

## Vault and persistence requirements

- Use a random 32-byte key, a fresh random 12-byte nonce for every encryption and a full 16-byte authentication tag. Authenticate a versioned envelope and the fixed provider/global-vault scope as associated data, preventing an encrypted entry from being moved to another provider. Reject malformed sizes/version/encoding and authentication failure with a generic unavailable response.
- Persist the key outside state.json and every API/report/export, with mode0600, expected runtime owner and a private parent. Create it exclusively and atomically; concurrent initialization must share the winning key. Existing ciphertext plus a missing, changed or unreadable key must block the vault, never regenerate a key or overwrite stored entries. Reject symlinks/unsafe file types and broad permissions rather than silently accepting an insecure key location.
- Store encrypted entries and the redacted audit event in one AtomicRepository transaction where possible. If separate files are used, an explicit journal/recovery contract is needed to prevent success without the audit or deletion being durable. Serialize concurrent save/delete/update operations and preserve unrelated tenant/job/session data. The present repository serializes within the single Node process; do not claim multi-process writer safety from that alone.
- Expose only fixed provider id, configured/not-configured state, timestamps, permitted budget metadata and operation/revision identifiers to authorized administrators. Never expose plaintext, key suffixes, ciphertext, nonce/tag, encryption-key paths or credential-derived fingerprints. Audit only actor, action, provider, time and outcome; never request payloads or crypto material. Existing tenant SSE/job/evidence projections must not receive global integration audit entries or vault internals.
- Redacted encryption is not protection against theft of the entire data volume if it also contains the decryption key. State the threat model accurately and back up ciphertext and its private key together through the existing protected storage process. Do not put either into Git/build/runtime-package evidence. JavaScript-managed string memory is not guaranteed secure zeroization; do not claim otherwise.

## API and product correctness

Keep management endpoints inside the existing authenticated versioned API; do not add public edge exceptions. Require same-origin mutation/CSRF checks, no-store responses and strict request fields. Limit keys and provider ids before persistence; use a fixed Set/Map or Object.hasOwn, avoiding inherited-property names such as constructor/__proto__. Reject arbitrary endpoints, callback URLs, shell/path inputs and a generic test-connection fetch facility. Credentials are submitted once and cleared from UI input after successful save; no localStorage/sessionStorage or query-string persistence.

ProviderRegistry remains the adapter/capability authority. Saving Seedance, Higgsfield, CapCut or Gemini credentials must not set available=true, manufacture connection success, call a provider or bypass existing paid-execution/creative/release gates. FFmpeg and deterministic-test are not external API-key destinations. UI copy must distinguish “credencial guardada” from “integración disponible”. A delete must leave truthful unconfigured metadata and invalidate any future server-side credential cache.

Budget values are bounded, finite, nonnegative preferences in an explicitly identified unit/currency. Reject NaN/Infinity, negative values, unsupported currency and coercion of arbitrary strings. A stored budget is neither a spending authorization nor evidence of available credits; existing generation remains blocked when the adapter or required approval is absent. If a future adapter consumes credentials, expose decryption through a private server-only method and retain all execution approvals.

## Minimum changed-scope regressions

1. **Authorization matrix:** genuine host fallback and configured system_admin=true succeed; tenant owner/admin, can_create_tenants, configured host-operator without that flag, string “true”, forged body roles and unauthenticated callers fail. A live session loses access after admin revocation; a missing configured identity file fails closed.
2. **Secret containment:** save a unique canary key, then inspect redacted GET/mutation responses, stored state, audit, errors and tenant event projections. None may contain the canary or cryptographic/key-file internals; unauthorized users must not receive global configuration metadata.
3. **Crypto/recovery:** recreate the service using the same private directory and decrypt the saved fixture internally; overwrite uses a new nonce. Corrupted ciphertext/tag, provider-swapped envelope and missing/wrong key with existing entries fail closed without clearing or replacing prior data.
4. **Filesystem/concurrency:** key creation race preserves one usable key; unsafe key permissions/symlink/owner fail. Concurrent save/delete and a forced persistence failure produce a consistent vault/audit outcome and preserve unrelated state. These are temporary-directory fixtures, not live key or container changes.
5. **HTTP/input boundary:** the new mutation endpoints reject cross-origin/no-origin requests, unknown providers/fields, oversized keys, malformed JSON and invalid budget values. No request accepts an arbitrary URL or client privilege field.
6. **Truthful integration:** after credential/budget save, an unimplemented provider remains unavailable, paid submission remains gated, no adapter/network method was called and delete removes configured status. Add one focused UI check for authorized entry, hidden unauthorized controls, redacted display and cleared input; reuse existing unrelated browser evidence.

No material design blocker remains if these requirements are implemented. Verify only the changed vault/auth/API/UI behavior; do not rerun unrelated worker, range, release-history or public-deployment suites for this design review.
